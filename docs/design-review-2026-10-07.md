本次 review 基于 2026-10-07 的工作区，包含尚未提交的附件、文件库和预览实现。检查了客户端同步与持久化、会话和草稿状态、Chat/Work 的输入链路、认证续期、Owner 调度、附件生命周期，以及搜索、记忆和工作区的主要边界。这是沿关键数据流做的设计 review，不代表逐行审计了全部实现。

我的判断是：项目的主干可以保留，接下来最值得投入的是把几条生命周期接完整。现在，单个模块内部考虑得比较细，但“过期以后怎么办”“请求回来时用户已经切到哪里”“删除后还有哪些副本”“写盘失败以后还能不能重试”，在模块交接处出现了遗漏。这些遗漏已经能解释具体的用户问题。

**1. 删除文本附件后，原文还会继续发给模型。**

小文本直接放进上下文，原本是为了让模型读文件时少调用一次工具，这个目的成立。但这里把“如何给模型读取”变成了“如何永久保存”：图片和 PDF 保存引用，文本则在组装用户消息时复制了正文，随后进入 `loop_steps.request_messages/input_delta`。删除接口只清理附件记录和会话引用，后续请求里的普通文本块不再经过附件状态检查。

位置：[文本内联](/home/Bliod/Projects/Rust/RyzHub/crates/server/src/chat/media.rs:207)、[上下文落库](/home/Bliod/Projects/Rust/RyzHub/crates/server/src/chat/runner.rs:374)、[附件删除](/home/Bliod/Projects/Rust/RyzHub/crates/server/src/attachments/http.rs:294)。

我用本地模型 fixture 跑了“上传文本 → 发送 → 删除 → 再发送”。第二次请求仍包含文件中的唯一标记。这里残留的是平台自己复制的附件正文，不是模型上一轮回答中已经引用过的内容。

建议所有附件都存带 ID 的引用，在构造每次模型请求时统一展开。小文本仍然可以直接发给模型，只把展开时间后移；删除检查、大小预算和无权访问的处理也能共用一条路径。已有上下文需要兼容处理，不能仅修新消息的生成。对于模型已经写进回答、摘要或原生 harness 历史的内容，则应单独说明删除边界，避免承诺无法兑现的“遗忘”。

对用户可以这样说：“你把文件删掉以后，下一轮请求就不该再附上这份文件的原文。现在图片能做到，文本还做不到。我们需要统一文件的读取方式，让删除对不同格式都生效。”

**2. 正常登录过期会丢掉同步状态，续上登录也不会自动补回来。**

撤销权限时清掉私有缓存和待发命令，是正确的隔离措施。问题是服务端也把 access token 自然过期解释为 `SubscriptionRevoked`。客户端没有处理 `AuthExpiring`，只在 HTTP 返回 401 后尝试刷新；Rust 内核收到撤销就删除频道和该频道的待发命令。之后即使 Web 端拿到新 token、重新建立连接，重订阅也是从已经清空的频道集合里恢复，当前会话和用户频道都可能没有订阅。

位置：[过期后的撤销帧](/home/Bliod/Projects/Rust/RyzHub/crates/server/src/ws/mod.rs:256)、[客户端清理](/home/Bliod/Projects/Rust/RyzHub/crates/core/src/lib.rs:165)、[401 后才续期](/home/Bliod/Projects/Rust/RyzHub/client/lib/controller.dart:577)、[重连恢复订阅](/home/Bliod/Projects/Rust/RyzHub/crates/bridge/src/api.rs:234)。access token 当前有效期是 12 小时。

向真实 bridge 输入“即将过期 → 两个订阅撤销 → 新连接 Welcome”后，续期预警没有产生可交给宿主的动作；重连输出帧为 0，原来的待发命令也变成 0。这验证了帧处理链，尚未做浏览器连续打开 12 小时的端到端测试。

建议让连接层明确处理认证生命周期：过期前刷新并发送已有的 `AuthRefresh`；网络故障或凭据过期进入重新认证，实际资源权限撤销才触发私有数据清理。还需要把“当前希望订阅哪些频道”与“已经拿到的频道投影”分开，认证恢复后重新鉴权并建立订阅。刷新失败也应回到明确的登录状态，而不是无限显示重连。

可以这样解释：“登录需要续一下，不代表你失去了这个对话的访问权限。这两件事现在走了同一个清理分支，所以连接恢复了，消息却可能不再更新。”

**3. 会话虽然有各自的 actor，领取会话的总循环仍会被一个锁卡住。**

每个会话只允许一个 Owner 写入，能保证命令有序，也能阻止旧执行者继续写状态。这个设计值得保留。但总调度循环直接 `await claim()`；领取租约的 `UPDATE channels` 一旦等行锁，整个循环就不能继续处理其他新会话的唤醒、领取和用户频道 outbox。

位置：[总调度循环](/home/Bliod/Projects/Rust/RyzHub/crates/server/src/owner/mod.rs:77)、[领取租约](/home/Bliod/Projects/Rust/RyzHub/crates/server/src/store/events.rs:249)。[项目回收](/home/Bliod/Projects/Rust/RyzHub/crates/server/src/projects.rs:614)会在持有频道锁时调用执行节点，是可能拉长等待的实际路径。

验证时先锁住会话 A 的频道行，确认 Owner 已经在领取 A 时等待，再提交并唤醒 B。B 在两秒观察窗口内一直排队，释放 A 的锁后才得到命令结果。影响范围是这个 Owner 进程的总调度；已经运行的其他 actor 有自己的循环，并不等于所有现有任务都停止。

建议领取候选会话时使用不会等待被占用行的方式，例如先 `FOR UPDATE SKIP LOCKED` 再更新；也可以把领取工作放进有并发上限、按会话去重的任务集合。总循环只做分派，outbox 独立推进。并发必须有上限，避免把锁等待换成数据库连接池耗尽。

可以这样说：“一个会话正在收尾，不应该让另一个会话也等着。现在执行过程分开了，但入口还排在同一条队伍里，需要把入口的等待也隔开。”

**4. 流式更新的成本取决于看过多少历史，而不只是这一条消息。**

Rust 统一处理顺序、去重和游标，Flutter 接收变化，这个分工很好。目前 bridge 为了找出变化，先复制所有缓存频道中每条 Item 的 revision 和长度，应用帧后再扫描一遍所有频道，并为每个频道输出 actions/runs。遇到持久事件或 ACK，还会序列化整个 Engine，由 SQLite/IndexedDB 替换一个大 JSON 值。

位置：[更新前全量扫描](/home/Bliod/Projects/Rust/RyzHub/crates/bridge/src/api.rs:198)、[更新后扫描和整库序列化](/home/Bliod/Projects/Rust/RyzHub/crates/bridge/src/api.rs:245)、[Web 缓存写入](/home/Bliod/Projects/Rust/RyzHub/client/lib/storage/cache_web.dart:25)。Flutter 上层又从统一的 `notifyListeners` 重建主页，在 [conversationView](/home/Bliod/Projects/Rust/RyzHub/client/lib/ui/home.dart:777) 重新排序、组织时间线。

探针为每个频道放 100 条、每条 1 KiB 的文本，只向一个频道增加一个字符，再更新一条持久 Item：

| 缓存频道数 | 缓存 Item 数 | 单次 Delta 返回的频道数 | 单次持久更新生成的缓存 JSON |
|---|---:|---:|---:|
| 1 | 100 | 1 | 118,973 B |
| 20 | 2,000 | 20 | 2,379,893 B |
| 100 | 10,000 | 100 | 11,907,173 B |

Debug 构建中，100 个频道的那次 Delta 处理约 23 ms。这不是手机或 release 性能结论；可以确定的是扫描范围和写入量随全部缓存一起增长。桥接调用还是同步的，后续 Dart JSON 解码、组件构建和数据库写入尚未计入这个时间。

建议由 Engine 在应用事件时直接返回被修改的频道、Item、run 和 action。持久层按记录或频道保存，仍在一个本地事务中提交游标、投影和 outbox。加载过的历史另设可控的缓存预算。界面订阅当前会话或具体消息的变化，侧栏和输入框不必随着每个文本分片一起刷新。这里应保留原子性，不能为了减少写盘而先发命令、稍后再保存。

可以这样说：“你看过一百个会话，不应该让正在生成的一句话变慢。现在每次更新都会顺带检查旧会话，我们应该只处理真正变化的部分。”

**5. 发送完成时，清掉的是当前输入框，未必还是刚才发送的内容。**

等本地入队成功再清空输入框，是为了失败后还能重试。但等待期间输入框仍可编辑，完成后却直接 `input.clear()`。第一次发消息还可能先等创建会话的 HTTP 请求，这个窗口并不只是一个极短的同步调用。

位置：[Composer.send](/home/Bliod/Projects/Rust/RyzHub/client/lib/ui/composer.dart:122)。测试中发送 `first message`，让 onSend 保持等待，再输入 `next draft`；放行发送后，后者变成空字符串。

建议发送时捕获草稿 ID、版本和内容；完成后只清除对应版本。更完整的做法是让发出的内容进入一条独立的本地待发记录，输入框立即开始下一份草稿。失败恢复也作用于那条记录，不能覆盖用户后来写的东西。

可以这样说：“我发出一句话以后继续打字，前一句发送完成不应该把后一句删掉。清空操作需要认准它对应的是哪一份草稿。”

**6. 工作区请求晚到，会把别的会话状态显示在当前会话里。**

全局保存一份 `workspace`，最初很容易接到界面上。但请求是并发的：打开 A 后再打开 B，A 的请求可能更晚回来。`select()` 虽然有 `_view` 检查，`refreshWorkspace()` 自身却没有检查返回结果属于哪个会话，仍会直接覆盖全局状态。

位置：[refreshWorkspace](/home/Bliod/Projects/Rust/RyzHub/client/lib/controller.dart:500)、[调用路径](/home/Bliod/Projects/Rust/RyzHub/client/lib/controller.dart:1036)。用两个可控制完成顺序的请求复现后，`selected` 是 B，`workspace` 却是 A。这样显示的检查点、恢复提示与按钮实际操作的对象可能不一致。

近期修复可以捕获会话 ID 和请求代次，只接收仍然有效的结果。随后把工作区状态和 busy 状态按会话保存，作业按 job ID 跟踪；页面只选择要显示哪一份。后台作业可以继续执行，页面切换不应改变它的归属。

可以这样说：“你已经切到 B，会话 A 晚回来的结果就不该占用 B 的页面。后台操作可以继续，但结果要回到自己的会话里。”

**7. “保存以后再发送”目前只约束第一次发送，没有约束重试。**

把命令队列和游标一起保存，然后再发网络请求，是整个断线恢复设计的重要前提。正常发送路径遵守了它；但 bridge 先修改内存 Engine，controller 才等待缓存写入。写入一旦失败，命令仍在内存队列中，而五秒定时器会直接调用 `retryPending()` 发出去。

位置：[内存先入队](/home/Bliod/Projects/Rust/RyzHub/crates/bridge/src/api.rs:172)、[缓存写入](/home/Bliod/Projects/Rust/RyzHub/client/lib/controller.dart:1201)、[绕过写入屏障的重发](/home/Bliod/Projects/Rust/RyzHub/client/lib/controller.dart:911)。这是代码路径确认；本轮没有实际制造 IndexedDB 配额耗尽或磁盘写入失败。

触发后，界面可能先提示本地保存失败，命令却稍后被执行。如果客户端在成功保存这条命令之前退出，重启后也没有原 CID 可以确认执行结果；用户再点一次发送会成为另一条命令。

建议第一次发送、定时重发和重连重发共用同一个持久化屏障。可以在 bridge 中区分已准备与已提交的变更，或者在驱动层把未成功落盘的整批状态挂起；缓存失败期间不发送其衍生的网络帧。不要只给定时器加一个错误字符串判断，游标和投影也需要明确的提交状态。

可以这样说：“既然界面告诉我这条消息没保存成功，它就不该在几秒后悄悄发出去。重试也必须遵守第一次发送的保存规则。”

**8. 本地入队成功和服务器接受成功，在界面里还没有分清。**

输入框在 `hub.send()` 完成本地入队后就清空。此后若服务器因附件已删除、并发上限或配置变化拒绝命令，内核会移除该命令，只留下一个错误码。bridge 没有把 CID、目标会话和原始输入一起交给 UI，因此用户既看不到一条明确失败的消息，也没有可靠的“恢复编辑”。配置拒绝甚至通过 `_pendingConfig.clear()` 清除所有会话的乐观设置。

位置：[不可重试拒绝的处理](/home/Bliod/Projects/Rust/RyzHub/crates/core/src/lib.rs:154)、[只有单个错误字符串的 Update](/home/Bliod/Projects/Rust/RyzHub/crates/bridge/src/api.rs:12)、[全局配置清理](/home/Bliod/Projects/Rust/RyzHub/client/lib/controller.dart:1261)。这条结论来自调用链检查，没有另跑一次浏览器拒绝消息的集成场景。

服务端对同一 CID 保留原结果是合理的，不能把已经拒绝的 CID 无限重发。需要补的是客户端命令记录：保留 `queued / accepted / rejected` 状态、目标会话和输入，用结构化命令结果更新它。可重试传输失败沿用 CID；用户修正一条已被最终拒绝的消息后，再创建新 CID。配置回滚也只影响对应命令和会话。

可以这样说：“消息发不出去没关系，但你写的内容应该还在，并且能看出是哪一条出了问题。现在只剩一个页面提示，恢复起来太费劲。”

**结构调整可以围绕这些问题逐步进行。**

前端最有价值的拆分，是把状态按归属放好。`HubController` 可以逐步成为页面协调入口：连接与认证由一个 session 对象管理；同步引擎负责频道投影和命令提交；草稿保存文本、附件和版本；工作区作业按会话和 job ID 管理。再给 bridge 返回值增加类型明确的变化集合与命令结果。这样拆的收益是前面的续期、串位、清空和错误归因都能在对应边界内解决，不需要先更换 Flutter 状态管理框架。

后端的 [项目回收](/home/Bliod/Projects/Rust/RyzHub/crates/server/src/projects.rs:593) 和 [附件 GC](/home/Bliod/Projects/Rust/RyzHub/crates/server/src/attachments/gc.rs:17) 还在数据库事务里等待执行节点或对象存储。锁的目的分别是防止恢复与清理冲突、防止最后一个内容引用被并发重用，不能简单把网络调用搬出去就算修好。可以复用工作区已有的作业思路：先持久化不可恢复的清理状态和操作代次，提交短事务，再做可重试的外部删除，最后确认完成；对内容地址的删除还要保留引用保护。优先缩短项目级清理事务，避免一次处理很多会话时把频道锁长时间攥在手里。

另外有两处值得在相关代码调整时一起整理：[Gateway 的 feed map 锁](/home/Bliod/Projects/Rust/RyzHub/crates/server/src/ws/hub.rs:81)覆盖了 NATS flush 和数据库读取，可以换成按频道共享的初始化任务；[BlobStore 配置](/home/Bliod/Projects/Rust/RyzHub/crates/server/src/workspace/mod.rs:39)每次都重新构造，S3 场景可以在 App 启动时建好客户端，后续只克隆并加租户前缀。这两项本轮没有做并发或 S3 性能测量，属于有明确代码依据的改进方向，不计入上面的已复现缺陷。

**这些已有设计值得继续沿用。**

- Rust sans-IO 内核统一处理序号、UTF-8 字节偏移、重复 Delta 和最终快照，能减少三端各自实现同步规则的风险。应优化它输出变化的方式。
- PostgreSQL 保存权威状态，命令结果、投影与事件在事务里提交，NATS 负责实时传递。这个组合能给重试和丢包提供明确的恢复依据。
- 会话 Owner 的 epoch fencing、运行配置与项目内容的快照，有助于把“当前设置”和“已经开始的运行”分开。上面的调度问题可以在领取阶段解决。
- 搜索结果回查实时来源权限，版本化发布索引，能避免删除与权限变化被异步索引拖延。全文在 embedding 失败时仍可用，也符合实际使用需要。
- Chat 和 Work 分别保留 provider/harness 的原生上下文，对外输出统一时间线，是合理的边界。跨提供方改成新对话的限制有上下文格式依据；不必为了看起来统一而丢失原生能力。

建议落地顺序是：先补附件撤销和认证恢复，再修 Owner 调度隔离；随后把草稿、命令提交与工作区结果的归属明确下来，最后做增量 bridge 和缓存迁移。每一步都可以有独立验收，迁移缓存时保留未确认命令，不能用清空缓存来绕过兼容性。

**验证范围。**
